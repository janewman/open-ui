## User-facing problem

Carousels are one of the most deployed interactive patterns on the web — and one of the most inconsistent. As @flackr noted at TPAC 2024: "if you look up 'should I use a carousel', the common answer is no."

The harms start with keyboard divergence. Every library invents its own model — some use Arrow keys, others Tab, many trap focus or let it reach invisible **slides**. Users learn one site's carousel and re-learn the next.

Screen readers announce carousels inconsistently; as @gmjellin reported in [ARIA #1617](https://github.com/w3c/aria/issues/1617): "We have done pretty extensive user testing with that pattern and all of our users had difficulty navigating." Today a single slide requires `role="group"`, `aria-roledescription="slide"`, and a meaningful `aria-label` — multiplied across every slide. The platform should supply this boilerplate automatically. Focus traps and lost-place-on-resize bugs persist because each library reimplements scroll-snap focus management independently.

CSS Overflow Level 5 introduces controls (`::scroll-marker`, `::scroll-button`) that are visually flexible but semantically rigid; ARIA cannot be applied to them; their accessible-name story is painful; `document.activeElement` becomes unreliable when they are focused; they cannot be removed from the tab order without removing them from the accessibility tree. (See [Sarah Higley, *On the design of CSS carousels*](#references-and-acknowledgements).) The CSS AAM gap ([ARIA #2496](https://github.com/w3c/aria/issues/2496)) is one facet of a broader structural problem: CSS pseudo-elements are the wrong primitive for interactive controls that need varied semantics. An HTML element addresses these head-on.

Real carousels on the web take many semantic shapes — galleries, slideshows, tabbed panels, navigation strips — each requiring different ARIA roles, keyboard models, and focus handling. The `<carousel>` element uses a `pattern` attribute to select the right shape declaratively, rather than forcing authors to assemble ARIA by hand or accept a one-size-fits-all mapping.

Autoplay introduces additional harms that merit their own design work. This proposal defers autoplay to a [future additive layer](#future-backwards-compatible-additions) and focuses on four `pattern` values — `gallery` (default), `slideshow`, `tabs`, and `navigation` — that cover the most common carousel shapes.

## How carousels are built today

### Hand-rolled and library carousels
Most carousels ship as JavaScript libraries, each with its own ARIA mapping, keyboard model, and autoplay behavior, making accessibility opt-in.

### The APG carousel pattern
The [APG Carousel pattern](https://www.w3.org/WAI/ARIA/apg/patterns/carousel/) defines a reference contract — `role="group"` slides, `aria-roledescription="slide"`, and an AT interaction model. It is a recipe, not a primitive; authors must assemble a dozen attributes, and most do not.

### CSS carousels
[CSS Overflow Level 5](https://drafts.csswg.org/css-overflow-5/) introduces `::scroll-marker-group`, `::scroll-marker`, and `::scroll-button()`, available in Chrome 135. These provide layout and scroll behavior but no implicit ARIA roles, keyboard model, or autoplay management. As [ARIA #2496](https://github.com/w3c/aria/issues/2496) observes: "there is no formal CSS AAM." Beyond the missing AAM, the CSS-pseudo approach has structural accessibility problems: indicators and prev/next controls cannot carry custom ARIA, must derive their accessible names through the painful `content: '' / 'name'` mechanism (which breaks user translation, reader mode, and localization tooling), and break standard focus-management scripts that rely on `document.activeElement` and DOM querying.

### Framework custom elements
Frameworks offer `<my-carousel>` custom elements, each with its own role mapping and keyboard contract and no cross-framework AT guarantee.

## The `<carousel>` element

### Minimal example

```html
<carousel aria-label="Product images">
  <figure><img src="shoe-1.jpg" alt="Running shoe, side view"></figure>
  <figure><img src="shoe-2.jpg" alt="Running shoe, top view"></figure>
  <figure><img src="shoe-3.jpg" alt="Running shoe, sole"></figure>
</carousel>
```

**What to notice:**
- Only `aria-label` is needed — slide roles, counting labels, and controls are all implicit. The carousel is accessible by default.
- The `pattern` attribute defaults to `gallery`; explicit values are `gallery`, `slideshow`, `tabs`, and `navigation`.
- The user agent applies implicit ARIA roles, keyboard navigation, and focus management automatically per the selected pattern.

### Anatomy
`<carousel>` is **flow content**. A **slide** is any direct element child that is a flow content container: `<article>`, `<aside>`, `<blockquote>`, `<details>`, `<div>`, `<figure>`, `<footer>`, `<form>`, `<header>`, `<nav>`, `<section>`, or a wrapping list (`<ul>`, `<ol>` — the list itself is one slide). Autonomous custom elements (e.g., `<my-slide>`) that contain flow content are also valid slides. Customized built-in elements inherit slide eligibility from their base element.

Direct children that are replaced elements (`<img>`, `<video>`, `<canvas>`, etc.) or interactive elements (`<button>`, `<input>`, `<a>`, etc.) are carousel content but not **slides** — they keep their native semantics, receive no `role="group"`, no auto-label, and are excluded from slide navigation. Authors should wrap them in a container for full slide semantics.

`<script>`, `<style>`, and `<template>` children are never slides. The parser ignores whitespace, text, and comment nodes between slides (like `<select>` ignoring whitespace between `<option>`s).

Indicators and prev/next controls are best provided as HTML elements via `commandfor` (see [§Author-provided controls](#author-provided-controls-via-commandfor)). For thumbnail-strip indicators, authors use a sibling element or a sibling carousel (linking mechanism is an [open question](#open-design-questions)). CSS pseudo-elements `::scroll-marker-group` / `::scroll-marker` and `::scroll-button(prev)` / `::scroll-button(next)` per [CSS Overflow Level 5](https://drafts.csswg.org/css-overflow-5/) remain available for visual styling but are not recommended for accessibility-sensitive contexts; CSS pseudos cannot be ARIA-attributed and present focus-management challenges (see [Sarah Higley, *On the design of CSS carousels*](#references-and-acknowledgements)).

Non-slide direct children (e.g., a `<button commandfor>` placed inside `<carousel>`) retain their native sequential focus participation. They are reachable via Tab independent of the carousel's single tab stop on the current slide.

A slide is **navigable** when it is connected, its computed `display` is not `none`, and its computed `visibility` is not `hidden`. The set of navigable slides — the **navigable subset** — is what the `next`/`previous`/`goto-slide` commands, the current-slide cursor, and the auto-generated "N of M" label operate on. The user agent suppresses snap points for slides outside the navigable subset, so navigation reliably skips them.

Like any element with a roledescription, `<carousel>` is most useful to assistive-technology users when it has an accessible name. The accessible name follows the standard [accname-1.2](https://www.w3.org/TR/accname-1.2/) computation. An unlabeled `<carousel>` is valid (like an unlabeled `<section>`) and degrades to AT announcing "carousel" without further context.

### Implicit ARIA

The `pattern` attribute selects the carousel's semantic shape. Default value: `gallery`.

| `pattern` | Container role | Container `aria-roledescription` | Slide role | Slide `aria-roledescription` | Other |
|---|---|---|---|---|---|
| `gallery` (default) | `group` | `"carousel"` | `group` | `"slide"` | Auto-label "N of M"; `aria-live="polite"` on current slide. APG Carousel pattern. |
| `slideshow` | `group` | `"carousel"` | `group` | `"slide"` | Same as gallery; `inert` on off-screen slides + `aria-live` autoplay-aware (v2). |
| `tabs` | — (no implicit role on `<carousel>`) | — | `tabpanel` | — | The `<carousel>` is the panel container only. The tablist is an author-provided sibling (see [§Tabbed product info](#tabbed-product-info)). UA gives `commandfor` buttons `role="tab"`; UA labels tabpanels via `aria-labelledby` to the matching tab. UA manages `aria-selected` on the active tab. |
| `navigation` | — (no implicit role) | — | — (slides keep native role) | — | `<carousel>` is purely a scrolling container. Authors wrap in `<nav>` for landmark. Slides like `<a>` keep their native semantics. |

The `<carousel>` element uses `role="group"` rather than `role="region"` for `gallery`/`slideshow` patterns, avoiding landmark proliferation. Authors who want landmark status may add `role="region"` explicitly.

The slide role overrides the child element's native implicit role for `gallery`/`slideshow` patterns. For `navigation` pattern, slides retain their native roles. The rendered current slide carries implicit `aria-live="polite"` (for `gallery`/`slideshow`); user agents suppress the live-region announcement when keyboard navigation simultaneously moves focus to the new slide.

#### If author uses CSS pseudo-elements (not recommended for tabs/navigation patterns)

| Pseudo | Implicit role | Other |
|---|---|---|
| `::scroll-marker` | Per [CSS Overflow L5](https://drafts.csswg.org/css-overflow-5/) mode | Accessible name resolved per accname-1.2. In `tabs` mode: `aria-selected="true"` on active marker. |
| `::scroll-button(prev)` | `button` | UA-generated name: "Previous slide" (locale equivalent); `aria-disabled="true"` at first slide. |
| `::scroll-button(next)` | `button` | UA-generated name: "Next slide" (locale equivalent); `aria-disabled="true"` at last slide. |

**Note:** These mappings are constrained by what CSS pseudo-elements can express; for full ARIA control (custom roles, `aria-labelledby`, etc.), authors should use HTML controls via `commandfor`. User agents MUST render pseudo-elements visibly in Forced Colors mode.

### Keyboard and focus model

The user agent internally tracks the **current slide** — the navigable slide nearest the scroll-snap-alignment point. When `scroll-snap-type` is `none`, the user agent determines the current slide after `scrollend`. If the current slide leaves the navigable subset (DOM removal, `display: none`, or `visibility: hidden`), the user agent selects the next navigable slide (or previous if last; or `null` if empty). When the slide that currently holds focus leaves the navigable subset, the user agent moves focus to the new current slide.

The keyboard model varies by `pattern`:

- **`gallery` / `slideshow`**: The `<carousel>` element carries implicit `focusgroup="carousel"` — a token registered in the [focusgroup explainer](/components/scoped-focusgroup.explainer). The token provides: single tab stop via roving tabindex, inline-axis arrow-key navigation following writing mode, Home/End to first/last slide, no wrap, and memory. Tab from the current slide proceeds into its focusable descendants via standard sequential focus navigation.
- **`tabs`**: NO `carousel` focusgroup on the slide container. Slides (tabpanels) are individually tabbable per APG Tabs. The author-provided tablist sibling carries `focusgroup="tablist"` (existing token) for arrow-key navigation among tab buttons.
- **`navigation`**: No implicit focusgroup. Slides are individually tabbable, retaining their native focus participation.

Arrow-key navigation (for `gallery`/`slideshow`) triggers a scroll-snap settle; the user agent updates the current slide once the new slide reaches its snap-rest position. If the author overrides `scroll-snap-type` to `none`, the user agent determines the current slide after `scrollend`.

For `commandfor` button activations, focus remains on the button and assistive technology hears the new slide via the `aria-live` announcement on the current slide. When the slide that currently holds focus leaves the navigable subset, the user agent moves focus to the new current slide.

### Composition with CSS carousels

CSS Overflow Level 5 pseudo-elements (`::scroll-marker`, `::scroll-button`) compose with `<carousel>` for visual styling but should not be the primary navigation mechanism in accessibility-sensitive contexts. The recommended pattern is HTML controls via `commandfor` (see [§Author-provided controls](#author-provided-controls-via-commandfor)). The CSS pseudos remain available where the author has full control over context (decorative pagination, presentational scroll-snap UIs, etc.).

Switching from a CSS-only carousel to `<carousel>` requires changing one element name:
```html
<!-- Before: manual ARIA -->
<section role="region" aria-roledescription="carousel" aria-label="News">
  <div role="group" aria-roledescription="slide" aria-label="1 of 3">…</div>
  <div role="group" aria-roledescription="slide" aria-label="2 of 3">…</div>
</section>
<!-- After: implicit semantics -->
<carousel aria-label="News">
  <div>…</div>
  <div>…</div>
</carousel>
```

**Note**: the implicit role changes from `region` to `group`. Add `role="region"` if landmark status is required for the page's information architecture.

**What to notice:**
- Container `role`/`aria-roledescription`/`aria-label` plus per-slide `role`/`aria-roledescription`/`aria-label` boilerplate become implicit. CSS pseudo-element styles apply unchanged.

### Author-provided controls via `commandfor`

HTML controls via `commandfor` are the **primary recommended path** for accessible carousel navigation. Unlike CSS pseudo-elements, real DOM buttons can carry ARIA attributes, participate in `document.activeElement`, and be programmatically focused from external scripts.

#### Gallery pattern (default)
```html
<carousel id="gallery" aria-label="Featured">
  <section aria-label="Spring sale">…</section>
  <section aria-label="New arrivals">…</section>
</carousel>
<button commandfor="gallery" command="previous">←</button>
<button commandfor="gallery" command="next">→</button>
<button commandfor="gallery" command="goto-slide" value="0">First</button>
```

**What to notice:**
- Buttons can appear anywhere in the DOM; no JavaScript required.
- These commands are defined by `<carousel>` as part of its element-specific built-in command behavior, parallel to how `<dialog>` defines `show-modal` and `close`. See the [Invoker Commands explainer](/components/invokers.explainer).
- The `value` attribute serves double duty as both the form-submission value and the command parameter.

#### Tabs pattern
```html
<div role="tablist" focusgroup="tablist">
  <button commandfor="info" command="goto-slide" value="0">Overview</button>
  <button commandfor="info" command="goto-slide" value="1">Specs</button>
  <button commandfor="info" command="goto-slide" value="2">Reviews</button>
</div>
<carousel id="info" pattern="tabs" aria-label="Product info">
  <section aria-label="Overview">…</section>
  <section aria-label="Specs">…</section>
  <section aria-label="Reviews">…</section>
</carousel>
```

**What to notice:**
- The UA gives `commandfor` buttons `role="tab"` and manages `aria-selected`.
- The tablist uses `focusgroup="tablist"` for arrow-key navigation among tabs.
- For `pattern="tabs"`, `goto-slide` activates the corresponding tab.

#### Navigation pattern
```html
<nav aria-label="Categories">
  <carousel id="cats" pattern="navigation">
    <a href="/shoes">Shoes</a>
    <a href="/shirts">Shirts</a>
    <a href="/hats">Hats</a>
  </carousel>
</nav>
<button commandfor="cats" command="previous">←</button>
<button commandfor="cats" command="next">→</button>
```

**What to notice:**
- Slides keep their native link semantics — no role override.
- The `<nav>` wrapper provides the landmark; `<carousel>` handles scrolling.
- Commands scroll mechanically; no ARIA state change.

#### Command table

| Command | Behavior | `value` parameter |
|---------|----------|-------------------|
| `next` | Advances one slide within the navigable subset; no-op at last navigable slide | (none) |
| `previous` | Retreats one slide within the navigable subset; no-op at first navigable slide | (none) |
| `goto-slide` | Jumps to the slide at the given 0-based index among slide children in DOM order, if navigable. For `pattern="tabs"`, also activates the corresponding tab (`aria-selected="true"`) | Required: 0-based integer string; non-integer, out-of-range, or non-navigable values are a no-op |

`goto-slide` silently no-ops on invalid input because declarative HTML attributes cannot surface exceptions. If `commandfor` references a non-existent element, the command is silently ignored per the [Invoker Commands](/components/invokers.explainer) model.

**Event: `slidechange`.** A plain `Event` (bubbles: true, composed: false, cancelable: false) fires on the carousel after the current slide changes and reaches its rest position. `slidechange` fires after the `scrollend` event. It fires when the current slide changes due to: scroll-snap settle, keyboard navigation, `commandfor` activation, programmatic scroll, or DOM mutation that removes/hides the current slide. It does NOT fire on initial `<carousel>` connection. The user agent coalesces rapid navigations — only the final rest position fires `slidechange`. For `pattern="tabs"`, `slidechange` is the tab-activation event. The event has no payload in v1; a typed `CarouselSlideChangeEvent` with `slide`/`index`/`previousSlide`/`previousIndex` is deferred to a future addition.

### Progressive enhancement
A bare `<carousel>` works without JavaScript: implicit ARIA per `pattern`, scroll-snap navigation, keyboard navigation via the focusgroup `carousel` token (for `gallery`/`slideshow` patterns), `commandfor` controls, and pseudo-control affordances are all declarative. The user agent stylesheet sets `display: flex`, `overflow-inline: auto`, `scroll-snap-type: inline mandatory`, and `scroll-snap-align: start` on slide children. The `slidechange` event fires when the current slide changes; listening to it requires JavaScript but is the only JS-dependent feature in v1.

## Practical use cases

### Product gallery with thumbnail strip
```html
<carousel id="main" pattern="gallery" aria-label="Product photos">
  <figure><img src="product-1.jpg" alt="Front view"></figure>
  <figure><img src="product-2.jpg" alt="Side view"></figure>
</carousel>
```

**What to notice:**
- `pattern="gallery"` is explicit here (it is also the default when omitted).
- Linking a thumbnail strip to the main carousel is an [open question](#open-design-questions).

### Photo gallery with author buttons
```html
<carousel id="photos" pattern="gallery" aria-label="Photo gallery">
  <figure><img src="a.jpg" alt="Sunset over the lake"></figure>
  <figure><img src="b.jpg" alt="Mountain trail at dawn"></figure>
</carousel>
<button commandfor="photos" command="previous">←</button>
<button commandfor="photos" command="next">→</button>
```

**What to notice:**
- Author-provided prev/next buttons sit outside `<carousel>` and use `commandfor` to target it.

### Tabbed product info
```html
<h2 id="product-h">Product details</h2>
<div role="tablist" focusgroup="tablist">
  <button commandfor="product-info" command="goto-slide" value="0">Overview</button>
  <button commandfor="product-info" command="goto-slide" value="1">Specifications</button>
  <button commandfor="product-info" command="goto-slide" value="2">Reviews</button>
</div>
<carousel id="product-info" pattern="tabs" aria-labelledby="product-h">
  <section aria-label="Overview"><p>Lightweight running shoe…</p></section>
  <section aria-label="Specifications"><dl>…</dl></section>
  <section aria-label="Reviews"><ul>…</ul></section>
</carousel>
```

**What to notice:**
- `pattern="tabs"` gives each slide `role="tabpanel"`; `goto-slide` activates the matching tab.

### Netflix-style category strip
```html
<nav aria-label="Browse categories">
  <carousel pattern="navigation">
    <a href="/action"><img src="action.jpg" alt="Action"></a>
    <a href="/comedy"><img src="comedy.jpg" alt="Comedy"></a>
    <a href="/drama"><img src="drama.jpg" alt="Drama"></a>
  </carousel>
</nav>
```

**What to notice:**
- `pattern="navigation"` means no role override — `<a>` elements stay links; `<nav>` provides the landmark.

## Accessibility, i18n, privacy, and security considerations

### Accessibility

The CSS Overflow Level 5 pseudo-elements (`::scroll-marker`, `::scroll-button`) provide visually flexible carousel controls but have structural accessibility limitations documented by [Sarah Higley](#references-and-acknowledgements): they cannot be ARIA-attributed, their accessible-name mechanism (`content: '' / 'name'`) breaks user translation and reader mode, and focusable pseudos make `document.activeElement` and focus-management scripts unreliable. The `<carousel>` element addresses these by providing implicit ARIA per `pattern`, real-DOM controls via `commandfor`, and standard focus participation.

The `<carousel>` element provides implicit ARIA semantics matching the [APG Carousel pattern](https://www.w3.org/WAI/ARIA/apg/patterns/carousel/) (for `gallery`/`slideshow`) and APG Tabs (for `tabs`). Keyboard navigation follows the roving-tabindex model for gallery/slideshow and standard tablist conventions for tabs. AT announces slide changes via the implicit `aria-live="polite"` region on the current slide.

A carousel is most useful to assistive-technology users when it has an accessible name, but the first rule of ARIA applies: authors should not add `aria-label` when native HTML or existing ARIA mechanisms already provide naming. Recommended patterns, in order of preference:

```html
<!-- aria-labelledby pointing to an existing heading -->
<h2 id="featured-h">Featured products</h2>
<carousel aria-labelledby="featured-h">…</carousel>

<!-- aria-label when no nearby heading exists -->
<carousel aria-label="Product photos">…</carousel>

<!-- Inside a labeled figure: the figcaption labels the figure;
     no additional label on the carousel is needed -->
<figure>
  <figcaption>Photos from our trip to Iceland</figcaption>
  <carousel>…</carousel>
</figure>
```

Authors should not include the word "carousel" or "slide" in `aria-label` values — those words are conveyed by `aria-roledescription` and would produce redundant AT announcements.

User agents should honor `prefers-reduced-motion` by setting `scroll-behavior: auto` on `<carousel>` when the preference is active.

### Internationalization
RTL contexts flip inline navigation automatically (inherited from `focusgroup`). Vertical writing modes use the inline axis for both CSS `scroll-snap-type` and arrow-key navigation — the logical-property UA stylesheet adapts automatically, so vertical-writing-mode carousels work without authors changing anything. User agents localize auto-generated slide labels (e.g., "_N_ of _M_"), respecting the document's locale for numeral system and text direction.

### Privacy
No new privacy surface. The element does not access sensors, network resources, or user data.

### Security
No new security surface. The element does not load cross-origin resources or escalate privileges. `commandfor` reuses the [Invoker Commands](/components/invokers.explainer) security model.

## Future, backwards-compatible additions

This proposal ships four `pattern` values first. Each item below is out of scope for v1; each will land additively in future explainers, preserving the markup contract established here.

* **Slideshow autoplay** (`autoplay` attribute, `paused` IDL property): auto-rotation with a [WCAG 2.2.2](https://www.w3.org/WAI/WCAG22/Understanding/pause-stop-hide.html)-conformant pause control. Pairs with `pattern="slideshow"`.
* **`commandfor` commands for autoplay control** (`pause`, `play`, `toggle-autoplay`): paired with slideshow autoplay.
* **Cancelable `slidewillchange` event**: enables "are you sure?" navigation patterns.
* **JavaScript API for programmatic navigation**: `carousel.slides`, `carousel.currentSlide`, `carousel.currentIndex`, `carousel.goTo(index)`, `carousel.next()`, `carousel.previous()`.
* **Typed `CarouselSlideChangeEvent`**: upgrades the v1 plain `slidechange` event with `slide`, `index`, `previousSlide`, `previousIndex` properties.
* **Variant ARIA shapes beyond v1's four values**: `pattern="radio"`, `pattern="listbox"`, `pattern="wizard"`. Future patterns layer onto the `pattern` attribute additively without breaking v1 markup.
* **Further opt-out from CSS pseudos**: as the platform's pseudo-element accessibility story evolves, future specs may provide explicit mechanisms to suppress pseudo-control generation entirely.

Each addition is purely additive: existing v1 `<carousel>` markup continues to work unchanged when these land.

## Alternatives considered

### Status quo (libraries only)
Every library invents its own keyboard model and ARIA mapping. User testing ([ARIA #1617](https://github.com/w3c/aria/issues/1617)) shows consistent navigation failures.

### CSS carousels alone
CSS carousels deliver layout and scroll behavior but have structural accessibility problems beyond the missing AAM: pseudo-element controls cannot carry custom ARIA, their accname mechanism (`content: '' / 'name'`) breaks user-side translation and reader mode, and focusable pseudos make `document.activeElement` unreliable (see [Sarah Higley](#references-and-acknowledgements)). A native element provides `slidechange` observability, `commandfor` integration, `pattern`-aware ARIA mappings, the focusgroup `carousel` token, and real DOM controls that can be ARIA-attributed and programmatically focused.

### Combined CSS carousels + `focusgroup` + manual ARIA
Authors could combine CSS Overflow Level 5, `focusgroup`, a hypothetical CSS AAM, and manual ARIA. This inherits all CSS-pseudo structural problems (no custom ARIA on markers, painful accname, broken `document.activeElement`, no tab-order control without tree removal). It does not deliver `commandfor` integration, `slidechange`, or `pattern`-aware semantic selection.

### `<tabs>` element instead of `pattern="tabs"`
The `tabs` pattern is included in v1 because CSS Overflow Level 5's `tabs` mode for `scroll-marker-group` already creates a tab-shaped CSS-pseudo widget with all the structural problems documented by [Sarah Higley](#references-and-acknowledgements), and authors deserve a clean HTML alternative. A separate `<tabs>` element remains an open question; `pattern="tabs"` does not preclude it.

### `<section>` with `focusgroup` attribute
The `focusgroup` attribute provides keyboard navigation, but it does not carry semantic role assignment, automatic slide counting and labeling, marker accessibility, or built-in command support. Declarative command integration is element-native; carousel-specific commands need a host element with the carousel's semantics. An attribute on `<section>` cannot host element-specific commands without per-instance opt-in — a `<section focusgroup="...">` still requires manual `role`, `aria-roledescription`, and per-slide `aria-label`.

### `role="carousel"` alone
A role without a native element provides no keyboard behavior. The ARIA WG [closed #1617](https://github.com/w3c/aria/issues/1617), directing work to Open UI.

### Author-decorated `<section>` with manual ARIA
Requires ~3 ARIA attributes per slide plus container boilerplate, manual `aria-live` management, and bespoke JavaScript. `<carousel>` eliminates this boilerplate.

### Reusing `<details>` or accordion semantics
Carousels and accordions have different spatial models. Overloading `<details>` would mislead AT.

### A dedicated child element for slides
A `<carouselslide>` adds migration cost without semantic value beyond `role="group"`. Using existing container elements as slides avoids inventing a dedicated child element and composes with CSS carousel markup.

## Open design questions
<p class="question">What is the relationship between `<carousel>` and `<tabs>` / `<tabpanel>`? This proposal treats them as separate elements.</p>
<p class="question">Should the `next` command at the last slide wrap to the first? A `loop` attribute is under consideration.</p>
<p class="question">How should a thumbnail `<carousel>` link to a main `<carousel>`? Options: `for`, `controls`, or a sibling relationship.</p>
<p class="question">Should `<carousel>` interact with `loading="lazy"` on child images or preload adjacent slides?</p>
<p class="question">Should `<carousel>` support an explicit axis attribute that decouples keyboard navigation from CSS `scroll-snap-type`, or should vertical scrolling be handled exclusively via writing mode and CSS?</p>
<p class="question">How should `<carousel>` integrate with View Transitions when slides change?</p>
<p class="question">Should `<carousel>` participate in form submission, or is it explicitly non-form-associated?</p>
<p class="question">How should nested `<carousel>` elements behave? Should the outer carousel's arrow-key handling defer to the inner carousel when it has focus?</p>
<p class="question">How does `<carousel>` compose with Shadow DOM? Can a shadow root's slot distribution produce slides?</p>
<p class="question">How should `<carousel>` render in print media — all slides visible, or only the current slide?</p>
<p class="question">How should `pattern="tabs"` map a tab button to its corresponding panel? Index-based matching is fragile; explicit `aria-controls`/`id` pairing is more robust but more verbose. v1 should pick a mechanism.</p>
<p class="question">Should `pattern` values be changeable at runtime? If so, the UA must re-map ARIA atomically and reconcile focus position.</p>
<p class="question">Should there be a `pattern="radio"` / `pattern="listbox"` / `pattern="wizard"` in v1, or are these strictly future additions?</p>
